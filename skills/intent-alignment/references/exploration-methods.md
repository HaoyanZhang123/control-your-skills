# Exploration Methods｜需求误解诊断与主动探索参考

> **何时阅读**：用户表达不足以判断真实目标、上下文与字面含义冲突、多个解释竞争、用户难以描述主观偏好、反馈“就是不对”或反复返工时。
>
> **如何使用**：这是按需选用的方法库，不是要求依次跑完的检查清单。每次只使用能降低当前关键不确定性的方法。

## 一、先辨别：不确定性来自哪里？

| 类别 | 典型问题 | 值得检查的线索 | 优先处理 |
|---|---|---|---|
| 语义表达 | 错词、近义词、专业术语误用、多义词 | 上下文领域、对象、已有例子 | 将候选含义与具体任务对应；有依据才纠偏 |
| 指代与范围 | “这个”“上次那个”，局部/整体未指明 | 引用链接、当前文件、最近确认的对象 | 消解指代；会影响修改范围时确认 |
| 例子与要求 | “比如”“像……那样”被当成全部约束 | 示例想体现的特征，是否要求复刻 | 提炼要学习的维度，不机械复制 |
| 否定与保留 | “别太复杂”“其他不变”被过度泛化 | 显式否定项、基线功能、保留范围 | 明确禁止变更与允许变化的边界 |
| 目标与手段 | 用户先给实现方法但真正想解决其他问题 | 痛点、使用场景、预期效果 | 区分目的和方案，必要时提供替代路线 |
| 优先级取舍 | 多个目标不能同时极致满足 | 质量、时间、性能、成本、可维护性 | 解释冲突与代价，请用户决定关键取舍 |
| 事实或能力前提 | 以为工具支持某功能、误判实现成本 | 代码、文档、实际接口与权限 | 先查证再建议，未验证则标明 |
| 偏好未形成 | 用户“不知道哪种好” | 参考案例、受众、应用环境 | 展示可对比的实质差异，允许否定全部 |
| 隐含约束 | 以为“原功能当然保留”，但未写出 | 项目规范、现有行为、上下游依赖 | 保护有依据的既有行为，不任意添加新要求 |
| 上下文变动 | 新旧要求冲突、历史信息过时、跨任务串扰 | 任务范围、确认顺序、修改原因 | 同一范围的新明确要求通常优先；其他约束继续有效 |
| 过度推断 | Agent 用合理猜测代替用户选择 | 是否只有单一证据？是否另有解释？ | 保留假设身份，必要时做低成本验证或确认 |
| 反馈归因 | “不满意”被当成需求重做 | 原目标、已达成部分、实际质量问题 | 先区分误解、需求变化与执行失误 |

这些类别可能同时存在；不必为每一项贴标签，也不应把用户口语化视为错误。

## 二、几种高价值的探索方法

### A. 上下文意图重建

适用：用户用词不精确、指代含糊，或字面理解明显不符合前文目标。

1. 找出最新明确指令、既有目标、可访问的项目事实，以及用户过去已确认的相关决定。
2. 形成少量候选解释，分别说明各自会导致什么不同的行动或结果。
3. 比较证据：哪一种更符合当前任务？哪一项仍是推测？
4. 解释唯一且风险低时直接推进；若解释竞争且影响重大，明确指出关键分歧再询问。

**防错**：不要为证明某种解释合理而忽略反证；不要用“专业上通常如此”覆盖用户已明确表达的特殊要求。

### B. 目标—手段拆分

适用：用户给出了具体实现方法，但该方法可能无法解决核心痛点。

- 问题/痛点：什么现象需要改变？
- 目的/结果：改变之后用户会得到什么价值？
- 当前手段：提出的方法如何帮助实现该结果？
- 替代方案：是否有更低成本、更稳妥、对既有系统破坏更小的路线？

只在两者可能冲突时提出替代方案。用户已明确选择某个可行方法时，不反复重开方案争论。

### C. 概念翻译与可观察特征

适用：用户说“高级”“自然”“现代”“更自主”等抽象词，却无法指出具体实现。

做法：将抽象词拆成该领域中**可观察、可体验**的差异，并用任务内例子解释。例如“更自主”可能是自主拆任务、主动查资料、异常时恢复，**不必然**是扩大操作权限。

把这些解释视为候选含义，而不是直接写入需求；尽量用一个具体对比帮助用户判断。

### D. 差异方案与反例比较

适用：用户没有稳定偏好，不知道有哪些选择，或只知道不喜欢什么。

- 默认给出 **2–3 个具有本质区别** 的方向，不是同一方案的配色变体。
- 每个方向解释：解决哪类问题、突出什么、牺牲什么、什么情况下适用。
- 允许用户选择、混合、否定所有方案，或给出“不喜欢的地方”。
- 选项可以来自真实参考资料，也可以明确标为概念提案；不要把想象案例说成已经存在的产品。

### E. 诊断性反馈

适用：用户说“不对”“不够好”“你没理解”，却无法定位原因。

1. 先保留已被确认正确的部分，不默认全部推倒重做。
2. 对照原目标与当前结果，提出少量可检验的失败假设：理解偏差、执行缺陷、审美偏好、范围遗漏等。
3. 能查就先查；必要时展示局部修改对比或询问能区分假设的一个问题。
4. 找到偏差来源后再改，避免无依据的整套重写。

### F. 可逆原型/小实验

适用：偏好只有看见或使用结果才能确定，语言继续讨论收益有限。

- 先明确要检验哪个问题，再选最小样例、局部草图或独立试验分支。
- 在现有授权范围内行动；可能覆盖现有工作或产生意外副作用时先确认。
- 对比预期与观察，不把一次原型成功当成长期通用规则。
- 不让原型本身扩展成未经批准的完整开发。

## 三、关键假设核查清单

放慢的条件已在 `SKILL.md` 正文写明：存在未经验证的关键解释，且猜错会明显改变结果。满足时逐项核查：

- **证据**：这项理解来自用户明确说过的话，还是 Agent 推断？
- **替代解释**：是否还有与上下文一致、但导致不同动作的解释？
- **后果**：如果猜错，会改变文件范围、关键架构、用户偏好、费用或权限吗？
- **验证途径**：能否查文件、查事实、比对例子、做低成本试验？
- **决策权**：属于客观事实检查，还是必须由用户决定的偏好/授权？

处理顺序优先为：查证 → 安全比较/试验 → 必要的精准确认。不要凭空给出“理解准确率 95%”。

## 四、实际场景示例

### 场景 1｜仓库与 Skill 指代混淆

用户：“把这套机制加到这个 Skill 里。”同时发来 `control-your-skills` 仓库链接。

- **风险**：链接指向 Skill 集合仓库，并非一个确定的单独 Skill；可能是新增 Skill，也可能是修改其中已有 Skill。
- **推荐行为**：先查看仓库结构并结合前文判断；如果两种修改方向都会实质改变文件架构，应说明区别并让用户确认，而不是把自己推荐的方案写成用户原意。

### 场景 2｜抽象措辞被错误等同于技术方案

用户：“让 Agent 更自主一点。”

- **风险**：将“自主”直接解释为取消审批或扩大权限。
- **推荐行为**：结合实际痛点提出自主规划、自主检索、自我检查、异常恢复等不同含义；询问或比较哪一种能解决问题。操作授权独立处理。

### 场景 3｜目标与表面要求冲突

用户：“这个 Skill 限制太多，所有规则都删掉。”前文强调输出质量和建模正确性。

- **风险**：删除安全边界或正确性规则，反而损害目标。
- **推荐行为**：区分阻碍创造力的风格约束与保证正确性的约束，说明保留/放宽的取舍；不将建议代替用户的最终决定。

### 场景 4｜示例不是完整规格

用户：“想做类似 Notion 的笔记体验。”

- **风险**：将数据库、多人协作、模板系统等功能全部当成必须实现。
- **推荐行为**：先指出可借鉴的具体维度，如块编辑、信息组织、交互流畅度，再联系实际使用场景确认边界。

### 场景 5｜主观质量反馈

用户：“界面就是感觉不对。”

- **风险**：不断问审美词汇，或整套重做。
- **推荐行为**：能访问界面时先检查信息层级、布局密度、视觉一致性和交互路径；不能访问时索取必要参考。给出少量有依据的诊断与对比，保留已经正确的结构。

### 场景 6｜要求已经清晰

用户：“只把这个按钮向右移动 10px，其他地方保持不变。”

- **推荐行为**：按既有授权和项目规范直接执行并验证，不因为本 Skill 可用而重新讨论设计目标。

### 场景 7｜需求与实施问题应分流

用户：“功能定义没问题，但点击后报错。”

- **推荐行为**：交给调试流程查根因；除非后续证据显示需求理解本身错误，否则不要重新做需求探索。

### 场景 8｜用户明确限制操作

用户：“先讨论方案，别改项目。”

- **推荐行为**：允许基于已有文件分析、比较和建议；不借“做原型”之名修改项目文件或进行外部操作。
