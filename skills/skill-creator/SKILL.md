# 创建 DSH skill

## 0. 先判断该不该做成 skill

**该做**：同一套流程会被反复执行、需要多步判断、依赖领域里不显然的约定（schema、口径、评审标准）。

**不该做**：一次性的小任务；模型本来就会的通用知识；需要确定性计算或联网的动作（写脚本，让 skill 调用它）。

一个 skill 被加载，占的是**和其他所有上下文共享的窗口**。它必须能回答："这段话是模型本来不知道的吗？"

## 1. 三条核心原则

**简洁优先**。默认模型已经足够聪明，只补它不知道的。逐段自问："删掉这段，结果会变差吗？"不会就删。

**信息只住一处**。同一事实写在 SKILL.md 又写在 references，就会出现两份会漂移的版本。详细内容放 references，SKILL.md 只留主流程与"何时读哪份"。

**自由度分级**。按任务脆弱程度给约束，不要一律写死：

| 自由度 | 形态 | 用在哪 |
|---|---|---|
| 高 | 散文式原则 | 多种做法都成立、依赖上下文判断 |
| 中 | 带参数的脚本 / 伪代码 | 有惯用做法，允许变体 |
| 低 | 固定脚本、几乎无参数 | 操作易错、必须每次完全一致 |

窄桥装护栏，旷野给方向。

## 2. 目录形态

```
<name>/
├─ SKILL.md            必需。frontmatter + 正文
├─ references/         按需读的文档，不占常驻上下文
├─ scripts/            确定性代码，可执行而不必读入
└─ assets/             进入产出的素材（模板、字体、图片）
```

多数 skill 只用得到 `SKILL.md`，加上一份 `references/` 就够。**不建空目录**——`references/` 里没有真东西就别建，`assets/` 无素材就别建。

`SKILL.md` 控制在 150 行内。接近上限就拆到 `references/`，并在正文标清**什么条件下读哪一份**——不写清，拆出去的等于丢掉了。

## 3. frontmatter

```yaml
---
name: my-skill              # 必须与目录名逐字一致，小写 kebab-case
description: "……"          # 唯一触发面，见下
---
```

DSH 只强制 `name` 与 `description`，其余键忽略。可选键：`whenToUse`、`metadata`、`disable-model-invocation`、`user-invocable`。

**会毁掉整个 skill 的写法**：用驼峰 `disableModelInvocation` / `modelInvocable` / `userInvocable`。DSH 遇到直接抛错跳过该 skill，**只在日志告警**，模型侧表现为"这个 skill 没装"，很难查。必须写 kebab 形式。

**`description` 是唯一的触发面**——catalog 只向模型展示 name + description，正文只在触发后才加载。所以三段都要写进去：

1. 做什么；
2. 什么时候用（具体场景、文件类型、任务名）；
3. 不适用什么（负向边界，指向该用的别的 skill）。

"何时使用本 skill" 这类章节**不要写在正文**——正文加载时已经晚于触发决定了。

## 4. 渐进披露

| 层级 | 内容 | 何时进上下文 |
|---|---|---|
| 1 | name + description | 常驻 |
| 2 | SKILL.md 正文 | 触发时 |
| 3 | references / scripts / assets | 按需，脚本可执行而不读入 |

拆分三种常用形态：

- **按主题**：财务归一份、销售归一份，问到哪个读哪个。
- **按变体**：AWS 归一份、GCP 归一份，使用者选了才读。
- **按深浅**：正文给基础做法，进阶另开一份，正文写"需要 X 时读 Y"。

引用**只展开一层**，不要 references 里再链 references。超过 100 行的参考文件在顶部加目录。

## 5. 不要放进 skill 的东西

README、CHANGELOG、安装指南、迁移说明、速查卡——这些是给人看的仓库文档，不是给执行任务的 agent 看的。skill 里只留执行任务需要的信息。仓库根该有 README，skill 目录里不该有。

## 6. 创建流程

1. **先要例子**。至少两三个真实使用场景：使用者会怎么开口、期望产出什么。场景说不清就还没到写的时候。
2. **逆向拆解**。每个场景问："从零做一遍要写什么代码、查什么资料？"反复出现的 → `scripts/`；查过一次就忘的 → `references/`；产物里要复用的 → `assets/`。
3. **建目录**，只建用得上的那几个。
4. **先写 resources，后写正文**。素材落地后再写主流程，避免正文先写死一个素材提供不了的承诺。
5. **写正文**。祈使句，清单优于长句，不写背景铺垫。
6. **校验**：`python scripts/quick_validate.py <skill-dir>`，再按第 7 节自查。
7. **真实任务里用一次**，按卡住的地方改。没跑过的 skill 不算完成。

## 7. 交付前自查

- [ ] 目录名、frontmatter `name`、正文标题三者一致，且是 kebab-case。
- [ ] `description` 三段齐全（做什么 / 何时用 / 不适用），且不超 1024 字符。
- [ ] 正文 ≤150 行；拆出去的 references 在正文里都有"何时读"的说明。
- [ ] 没有空目录、没有 README/CHANGELOG 类附属文档、没有未填的占位符。
- [ ] 引用的脚本真的能跑，输出符合预期。
- [ ] 不写死本机绝对路径、不写死版本号。
- [ ] 事实分级：没验证的写"未验证"，不把设想写成现状。

## 8. 参考文件

需要时再读，不要一次全读：

| 文件 | 何时读 |
|---|---|
| `references/workflows.md` | 正文要写顺序流程或分支流程，需要结构范例时 |
| `references/output-patterns.md` | 产出格式要固定（严格模板）或要有范例对时 |

## 9. 边界

- 本 skill 管**内容与结构**。插件（plugin）开发、Host/UI 扩展点是另一套机制，不在此范围。
- 校验脚本只查形态（frontmatter、命名、体量），**查不出内容好坏**。绿了不等于写得好。
- 分发与版本发布按使用者仓库的既有约定，本 skill 不规定。
